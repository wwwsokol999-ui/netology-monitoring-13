# Домашнее задание «13. Системы мониторинга»

## 1. Минимальный набор метрик

| Метрики | Что показывают |
| --- | --- |
| Внешняя HTTP-проверка, запросы в секунду, ответы по классам кодов, таймауты и задержка p95 | Доступность платформы, нагрузку и то, с какими задержками и ошибками сталкивается клиент. |
| Загрузка CPU по ядрам, длина очереди выполнения с учётом числа vCPU | В какой момент вычислительная нагрузка насыщает процессор и начинает увеличивать время ожидания. |
| Число заданий в очереди, успешные и неуспешные вычисления, время от подачи задания до готового отчёта p95 | Растёт ли очередь и получают ли пользователи результат в срок. При асинхронном API HTTP 202 сообщает только о приёме задания. |
| Свободные байты и inode на разделе отчётов, ошибки записи | Хватит ли места для новых файлов. При исчерпании inode создать файл не получится даже при наличии свободных байтов. |

Проверка полного сценария периодически запускает небольшое вычисление и скачивает сформированный отчёт. Она проверяет результат так, как его видит клиент. [Google SRE Workbook](https://sre.google/workbook/implementing-slos/).

## 2. Дашборд для продуктового менеджера

Предложу дашборд SLI/SLO с фактической долей успешно завершённых заданий, долей отчётов, выданных в срок, и p95 времени до готовности. Если есть SLA, рядом покажу договорный порог, период расчёта и статус выполнения. Например, внутренний SLO может требовать, чтобы за 30 дней не менее 99% валидных заданий завершались выдачей доступного отчёта в согласованный срок. На дашборде видны фактический процент, тренд и остаток бюджета ошибок. [Google SRE Workbook](https://sre.google/workbook/implementing-slos/).

## 3. Ошибки приложений без отдельного бюджета на логи

Настрою структурированные ошибки в stderr и сохранение в уже доступном журнале, например journald или логах контейнеров с ротацией. Разработчики получат доступ на чтение к журналу своего сервиса. Уведомления о новых типах ошибок и всплесках будут приходить в существующий рабочий канал. В записи будут сервис, версия, время, тип исключения, stack trace и ID запроса. Секреты и персональные данные фильтруются. Локальное хранение ограничено сроком ротации и зависит от доступности узла.

## 4. Почему доля 2xx может быть 70% при отсутствии 4xx и 5xx

В знаменателе есть ответы, которые отсутствуют в числителе. Например, при 700 ответах 2xx и 300 ответах 3xx формула покажет 70%. Нужно проверить распределение кодов и определить, какие ответы считать успешными по договору и сценарию клиента. Если 3xx — штатный результат для выбранных запросов, учитываем их по согласованным правилам. Если клиента интересует конечный отчёт, измеряем успешное получение отчёта с учётом необходимых перенаправлений. Фактическую долю измеряет SLI, а 99% — целевой порог. [Google SRE Workbook](https://sre.google/workbook/implementing-slos/).

## 5. Pull и push

| Модель | Плюсы | Минусы |
| --- | --- | --- |
| Pull | Центр задаёт частоту опроса. Ошибка опроса сразу даёт сигнал о недоступности цели. Удобно собирать метрики долгоживущих сервисов. | Нужен сетевой доступ от сборщика к цели и актуальный список целей. Короткоживущий процесс может завершиться между опросами. |
| Push | Инициатор может работать за NAT и передавать данные по исходящему соединению. Удобно отправлять результаты коротких задач и данные с периферии. | Получателю нужно справляться со всплесками. Для сетевых сбоев нужны буферы и повторные попытки. Отсутствие данных проверяют отдельно, например по heartbeat. |

## 6. Классификация систем

| Система | Модель | Как работает |
| --- | --- | --- |
| Prometheus | В основном pull | Сервер опрашивает endpoints. Короткие задачи могут отправлять данные в Pushgateway, а Prometheus опрашивает этот шлюз. [Документация](https://prometheus.io/docs/introduction/overview/). |
| TICK | Push от агента в хранилище | Telegraf собирает метрики и отправляет их в InfluxDB. Отдельные входы Telegraf сами опрашивают источники. [Документация](https://docs.influxdata.com/telegraf/v1/output-plugins/influxdb/). |
| Zabbix | Гибрид | Пассивный агент отвечает на опрос сервера или прокси. Активный агент сам отправляет результаты. [Документация](https://www.zabbix.com/documentation/current/en/manual/concepts/agent). |
| VictoriaMetrics | Гибрид | VictoriaMetrics принимает данные по push, а vmagent умеет и принимать данные, и опрашивать Prometheus-совместимые endpoints. [Документация](https://docs.victoriametrics.com/vmagent.html). |
| Nagios Core | Гибрид | Активные проверки инициирует Nagios. Результаты пассивных проверок присылают внешние процессы. [Активные проверки](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/activechecks.html) и [пассивные проверки](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/passivechecks.html). |

## 8. CPU в Data Explorer

Выбраны `telegraf.autogen`, измерение `cpu`, хост `telegraf-getting-started` и поле `usage_system`. Окно наблюдения уменьшено с 1 часа до 5 минут. Группировка по времени заменена с автоматической на 10 секунд. Запрос отфильтрован по `cpu-total`, чтобы строить один общий ряд по CPU. [Документация Data Explorer](https://docs.influxdata.com/chronograf/v1/guides/querying-data/).

```sql
SELECT mean("usage_system") AS "CPU system %"
FROM "telegraf"."autogen"."cpu"
WHERE time > :dashboardTime: AND time < :upperDashboardTime:
  AND "host" = 'telegraf-getting-started'
  AND "cpu" = 'cpu-total'
GROUP BY time(10s) fill(null)
```

## 9. Метрики Docker

Устаревший блок Docker в конфигурации Sandbox заменён на актуальную конфигурацию. Сокет подключён только к контейнеру Telegraf. Доступ выдан через числовой GID группы сокета, режим `privileged` не использовался. После пересоздания Telegraf в `telegraf.autogen` появились `docker_container_blkio`, `docker_container_cpu`, `docker_container_mem`, `docker_container_net` и `docker_container_status`. Запрос по `docker_container_cpu.usage_percent` вернул данные, на скриншоте виден график. [Telegraf Docker Input Plugin](https://docs.influxdata.com/telegraf/v1/input-plugins/docker/).

```toml
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```
